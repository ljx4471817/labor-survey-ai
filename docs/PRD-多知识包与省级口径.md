# PRD：多知识包与省级口径

## 1. 背景与目标

劳动力 AI 助手将逐步从贵州扩展到全国。国家制度、指标定义和通用填报规则应全国共享，但个别指标在不同省可能有不同解释或操作口径。现有系统只有一个全局知识库，检索、日志、热点和管理配置均没有知识包维度。

目标：

1. 支持一个全国基础知识包和多个省级知识包。
2. 新增账号按所属省份自动关联省级知识包。
3. 省级内容可确定性覆盖全国同规则内容，不靠检索分数随机决定。
4. 知识包可独立构建、校验、发布、回滚和分省灰度。
5. 后台提供知识包管理、省份绑定、版本发布和审计能力。

非目标：

- 第一版不在网页中直接编辑 QA 或上传生产知识内容。
- 第一版不支持账号级知识包覆盖。
- 不把标准调查点目录、白名单、会话、测验、LLM 配置纳入知识包。
- 不要求一次性导入全国全部调查点数据。

## 2. 核心概念

| 概念 | 定义 |
|------|------|
| 全国基础知识包 | 国家制度、指标定义、通用填报指导 |
| 省级知识包 | 某省特有解释、地方操作口径和差异规则 |
| 知识包 | 可独立构建、发布和回滚的内容单元，包含 QA、来源内容、chunk、索引和 eval |
| 省级行政区划目录 | 全国省级代码、规范名称和兼容别名，仅用于稳定识别省份 |
| 标准调查点目录 | 省/市/县/乡/社区调查点集合，按省逐步导入 |
| 业务规则键 `rule_key` | 同一业务规则的稳定标识；同键省级内容覆盖全国内容 |
| 全局知识条目键 | `kb_id + entry_id`，用于日志、热点和反馈归因 |
| 兼容版本组合 | 某省实际使用的“全国包版本 + 省级包版本”配对 |

## 3. 已确认决策

### 3.1 内容结构

- 采用全国基础包 + 省级覆盖包。
- 当前 `knowledge-base/` 不得原样整体标记为全国包；先人工拆分地方内容。
- 已发现 `贵阳调查队填报规范指引` 等地方口径候选，需进入贵州包复核。
- 全国包只收录国家制度、全国培训和通用规则；地方解释进入省级包。
- `indicator_catalog.json`、年度 `migration_map` 保持全国共享，不在每包复制。

### 3.2 覆盖规则

- 省级覆盖条目必须声明稳定 `rule_key`。
- 全国与省级出现相同 `rule_key` 时，省级条目确定性优先。
- 同一规则的多个问法共享 `rule_key`，省级覆盖该规则的全部全国问法。
- 被覆盖全国条目保存在审计快照中，不作为并列结论展示。
- 回答明确标注省级口径，省级 `source` 首要展示，全国来源仅作辅助。

### 3.3 省份绑定

- 绑定主键为省级行政区划代码，不以省名字符串作为主键。
- 省名、简称作为显示和兼容别名。
- 省级行政区划目录与 `region_points.json` 解耦。
- 新增/编辑账号必须来自标准调查点目录并生成有效 `province_code`。
- 已知别名自动归一；无法识别的存量账号标记“省份待校正”，暂用全国包并告警。
- 问答每次按账号当前省份动态解析，不在账号表冗余保存 `kb_id`。
- 第一版禁止账号级知识包覆盖。

### 3.4 知识包版本

- 省份绑定到知识包 ID，不绑定具体版本。
- 每个知识包包含多个不可变版本，包上维护当前发布版本指针。
- 同一知识包可被多个省共享。
- 草稿、构建失败或 Eval 失败版本不得进入问答。
- 省份或知识包身份变化时自动开新会话；同一包仅版本升级时可继续旧会话。
- 消息来源快照记录实际 `kb_id / release_id / global_entry_key`。

### 3.5 索引与检索

- 每个知识包独立维护 Chroma 和 BM25 索引。
- 问答并行检索全国包和账号绑定的省级包。
- 显式 `rule_key` 覆盖优先于分数融合。
- 无覆盖关系的条目按现有 Hybrid/RRF 规则融合。
- 跨包条目必须使用全局知识条目键，避免不同包三位 QA ID 冲突。

### 3.6 版本兼容

- 省级版本记录其基于的全国版本。
- 全国升级后先进行 `rule_key`、indicators、source 兼容检查。
- 省级包未复核时，该省继续使用最后一个兼容版本组合。
- 未绑定省级包的省份直接使用最新全国版本。
- 管理端显示省份制度版本落后、待复核项和兼容状态。

### 3.7 失败策略

- 当前版本加载失败时使用该知识包最后一个已验证可运行版本，并告警。
- 没有任何可用省级版本时明确失败，不静默回退全国包。
- 全国包不可用时服务失败。
- 绝不临时使用贵州或其他省知识包。
- 日志记录降级原因和实际使用版本。

### 3.8 构建、发布与权限

- 内容维护继续走 `validate -> build -> eval` 离线流程。
- 网页后台只展示构建报告并执行发布、回滚，不在 Web 请求中重建索引。
- 系统管理员可维护知识包、绑定省份、发布和回滚。
- 省级业务管理员只读查看本省版本、绑定和状态。
- 市级、区县管理员和普通用户无知识库管理入口。

### 3.9 数据与分析

- 新建独立知识包注册库，沿用 SQLite/PostgreSQL 双后端适配模式。
- 注册库保存知识包、版本、发布记录、省份绑定和管理审计。
- 查询日志增加 `kb_id / release_id / global_entry_key / override_used / fallback_reason`。
- 调查员热点只看当前省有效知识组合范围。
- 管理端支持按知识包、省份下钻；系统管理员可全国对比。

## 4. 知识包内容边界

知识包应包含：

- manifest：包 ID、类型、名称、版本、适用省份、状态、内容哈希；
- QA 条目及 `source / indicators / rule_key`；
- 制度、培训等来源内容和 chunk；
- 包内图片等静态资产，使用包隔离路径；
- Chroma、BM25 构建产物；
- eval 集和构建、评估报告。

不得包含：

- 白名单、手机号、账号和会话；
- 标准调查点目录；
- LLM、Embedding、提示词配置；
- Dashboard、反馈和测验业务数据。

建议目录：

```text

├── shared/
│   ├── indicator_catalog.json
│   └── migration_map*.json
```

## 5. 注册库数据模型

建议新建 `knowledge_admin.db`，后续可切换 PostgreSQL：

### `kb_packages`

- `id`：知识包 ID
- `name`：显示名称
- `kind`：national / provincial
- `status`：draft / active / disabled
- `current_release_id`：当前发布版本
- `created_at / updated_at / created_by / updated_by`

### `kb_releases`

- `id`：版本 ID
- `package_id`
- `version`
- `artifact_path`
- `content_hash`
- `based_on_national_release_id`
- `build_status / eval_status`
- `created_at / published_at / created_by`

### `province_kb_bindings`

- `province_code` 主键
- `package_id`
- `updated_at / updated_by`

### `kb_admin_audit`

- actor、action、target、before_json、after_json、created_at

## 6. 后台功能

新增 `kb-admin.html`，沿用统一 `admin-header + adminNav`：

1. **知识包列表**：名称、类型、当前版本、状态、适用省、最近构建。
2. **省份绑定**：按省级行政区划目录搜索、绑定、解绑、查看历史。
3. **版本与发布**：查看构建报告、Eval 报告、兼容状态；执行发布、回滚。
4. **知识包预览**：指定包和测试问题查看检索结果，不修改真实账号。
5. **审计记录**：查看配置、发布、回滚和绑定变更。

## 8. 检索流程

1. 鉴权获取账号当前用户。
2. 将账号省份归一为 `province_code`；异常则告警并使用全国包。
3. 解析省份绑定和兼容版本组合。
4. 并行检索全国包、省级包。
5. 根据 `rule_key` 去除被省级覆盖的全国条目。
6. 对剩余结果做 Hybrid/RRF 融合。
7. 生成答案并展示省级优先来源。
8. 记录实际包版本、全局条目键、覆盖和降级信息。
9. 省份或知识包身份变化时自动创建新会话。

## 9. 制度年度更新

1. 全国共享指标目录和 migration map 只维护一份。
2. 先迁移并发布全国基础包。
3. 扫描所有省级包的 `rule_key / indicators / source`。
4. 各省完成人工复核和本省 eval。
5. 未完成省份继续使用旧兼容版本组合。
6. 复核通过后发布省级新版本并切换。

## 10. Eval 与测试门禁

每个待发布版本必须通过：

- 本包 Eval：`must_contain_any`、`should_not_contain` 全通过；
- 全国回归：省级发布不得破坏通用口径；
- 跨省隔离：A 省问答不得命中 B 省地方条目；
- 覆盖测试：同 `rule_key` 必须确定性选择省级内容；
- 回退测试：当前版本损坏时必须使用最后可用版本或明确失败；
- 双后端测试：注册库 SQLite/PostgreSQL 行为一致。

测试层次：

- 单测：省份归一、版本兼容、覆盖键、绑定解析、权限纯函数；
- 集成：注册库、管理 API、双索引检索、日志字段；
- E2E：账号创建到问答绑定、省份切换开新会话、发布回滚；
- 检索 Eval：全国、地方、跨省隔离三套集合。

## 12. 风险与控制

| 风险 | 控制 |
|------|------|
| 地方内容误入全国包 | 来源审核 + 跨省隔离 Eval |
| 新旧版本混用冲突 | 兼容版本组合 + 国家版本关联 |
| QA ID 跨包冲突 | 全局知识条目键 |
| 省名不一致 | 省级行政区划代码 + 别名归一 |
| 构建失败影响线上 | 离线构建 + 不可变版本 + 最后可用版本 |
| 管理误操作 | 系统管理员写权限 + 审计 + 发布/回滚 |
| 热点和反馈串省 | 日志带包版本，前台按省过滤 |
| 全国数据导入阻塞 | 省级目录与调查点目录解耦 |
