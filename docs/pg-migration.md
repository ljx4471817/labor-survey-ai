# PostgreSQL 迁移指南（阶段二）

> 目标：4 个持久化库从 SQLite 切到 PostgreSQL，**保留一条配置切回 SQLite 的能力**。
> 数据搬家由服务器侧在本停机窗口内执行；本指南覆盖切换、验证、回滚全流程。

## 1. 原理

- `backend/app/persistence/db.py` 是唯一的连接创建点。它按 DSN 前缀自动判定后端：
  - `postgres://` / `postgresql://` 开头 → PostgreSQL（psycopg 3，`psycopg[binary]`）
  - 其它值 → SQLite 文件路径
- 每个库一个环境变量（值可以是 PG DSN，也可以是 SQLite 路径）：

| 库 | 环境变量 | 默认（未设置时） |
|---|---|---|
| 白名单 | `LSX_DB_WHITELIST` | `backend/data/whitelist.db` |
| 会话 | `LSX_DB_CONVERSATIONS` | `backend/data/conversations.db` |
| 问答日志 | `LSX_DB_QUERY_LOG` | `backend/data/query_log.db` |
| 测验 | `LSX_DB_QUIZ` | `backend/data/quiz.db` |

- **切库 = 改 `.env` + 重启；回滚 = 改回 `.env` + 重启。不回滚代码。**
- 未设置任何变量时行为与切换前完全一致（本地开发零影响）。

## 2. PG 主键策略说明

所有自增主键在 PG 侧使用 `GENERATED BY DEFAULT AS IDENTITY`（而非 `GENERATED ALWAYS`）：

- 迁移脚本需要**显式插入**从 SQLite 带来的 `id`，`GENERATED ALWAYS` 会拒绝显式插入；
- `BY DEFAULT` 兼顾显式插入与自动序列，迁移后由 `setval` 重置序列到 `max(id)`。

## 3. 服务器切换步骤（停机窗口内，硬上限 60 分钟）

```bash
# 0) 停服

# 1) 备份（既有流程：4 个 SQLite 文件 + 快照）

# 2) dry-run（默认模式；只读 SQLite，不写任何业务数据，但会在目标 PG 幂等建表 IF NOT EXISTS）
python backend/scripts/migrate_sqlite_to_pg.py \
  --sqlite-dir backend/data \
  --dsn-map '{"whitelist": "postgresql://...", "conversations": "postgresql://...", "query_log": "postgresql://...", "quiz": "postgresql://..."}' \
  --report-out reports/migration-dry-run.md

# 3) 确认 dry-run 报告全部"一致"后，正式迁移
python backend/scripts/migrate_sqlite_to_pg.py --apply \
  --sqlite-dir backend/data \
  --dsn-map '{...}' \
  --report-out reports/migration-apply.md

# 4) 改 .env：加 4 个 LSX_DB_* 变量（值 = PG DSN）

# 5) 重启服务

# 6) 切换后验收（实际跑过的命令；健康检查别只看 200，要确认 chroma_count>0）
curl -s http://127.0.0.1:8001/health
curl -s -o /dev/null -w '%{http_code}' https://laborforceai.xyz/login
curl -s -X POST http://127.0.0.1:8001/api/auth/login -H 'Content-Type: application/json' -d '{"phone":"<管理员手机号>"}'
# 带 token 再验：/api/admin/whitelist、/api/admin/whitelist/audit、/api/admin/whitelist/region-points、
#   /api/admin/usage/search、/api/admin/usage/trend、/api/admin/usage/gaps、/api/admin/feedback/stats、
#   /api/admin/quiz/scenes、/api/admin/quiz/list（quiz/stats 需要 quiz_id 参数）
#   /api/chat/conversations、/api/chat/hot-questions、/api/quiz/current
# 最后真跑一次 POST /api/chat，确认 PG 里 query_log 行数 +1
```

迁移脚本特性：

- **默认 dry-run**：不加 `--apply` 不写任何业务数据（但会在目标 PG 创建表结构；表为幂等 `IF NOT EXISTS`，重复执行安全）
- **只读打开 SQLite**（`mode=ro`），物理上不可能写坏源库
- 表清单自动发现（`sqlite_master`，排除 `sqlite_%`），不写死表名
- 逐表**行数 + 校验和**双比对（校验和顺序无关，NULL / 数值类型规范化），任一不一致退出码非 0
- 幂等：`--apply` 先 `TRUNCATE` 目标表再全量插入，重复执行结果一致
- 迁移完成后自动 `setval` 重置所有 IDENTITY 序列到 `max(id)`
- 报告（markdown）逐表一行 + 耗时，供窗口复盘

## 4. 切回 SQLite（回滚 ≤ 5 分钟）

```bash
# 1) 停服
# 2) .env 删掉（或注释）4 个 LSX_DB_* 变量 —— 回落默认 SQLite 路径
#    （原 SQLite 文件全程未被删除/修改，直接可用）
# 3) 起服 → 验健康
```

注意：回滚后 PG 里窗口期之后新写入的数据不会自动同步回 SQLite（本方案是"一次性搬"，
不做双写）。若窗口期内已有真实写入再回滚，需人工核对缺量。

## 5. 验证命令

```bash
# 单元测试（零配置 = SQLite）
cd backend && pytest tests/ -q

```

## 6. 已知差异 / 注意点

1. **REAL → DOUBLE PRECISION**：PG 侧 `retrieval_score` / `kb_score` 用 `DOUBLE PRECISION`，
   与 Python float 精度一致（PG 的 `REAL` 是 float4，会丢精度）。
2. **`PRAGMA`**：PG 不支持，适配层 SQLite 分支统一应用
   `journal_mode=WAL` + `busy_timeout=5000` + `timeout=10`；PG 分支跳过。
3. **`INSERT OR IGNORE`**：quiz_db 四处改双套 SQL，PG 用 `ON CONFLICT DO NOTHING`
   （不指定冲突目标列 = 捕获任意唯一约束冲突，语义等价；对应约束：
   targets 主键 `(quiz_id, phone)`、answers `UNIQUE(quiz_id, phone, q_id)`、scenes 主键 `name`）。
4. **异常类型**：业务代码统一捕获 `db.OperationalError` / `db.Error`（适配层把
   sqlite3 / psycopg 异常都翻译到这一组）。
5. **时间字段**：保持 UTC+8 ISO 文本字符串，不换 `timestamptz`（前端语义不变）。
6. **连接模型**：每线程一份底层连接（threading.local），连接创建集中在 `db.py`，
   将来换连接池只改这一个文件。阶段二不引入连接池 / pgbouncer / 读写分离。
7. **SQLite 侧统一 WAL**：query_log.db / gaps.py 原本未开 WAL，经由适配层后同样启用
   （WAL 是库级持久属性，读写行为兼容）。
8. **`stats_by_region` 潜在问题（原有，未改）**：level 非省且 `parent=None` 时
   WHERE 带占位符但无参数，会抛错。现有调用方都传 parent，行为不受影响，留待后续处理。

## 7. 明确不做（阶段三边界）

- 读写分离 / 只读副本 / 分片 / 多节点 / 主从高可用
- pgbouncer 等连接池中间件、监控告警体系
- ChromaDB 向量库迁移（与本次无关）
- 双写 / 实时同步
