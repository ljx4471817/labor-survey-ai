# 协作手册 · 维护者版

> 你（仓库拥有者）专用。核心三件事：**守住 main、管好密钥、让 PR 质量过关**。

## 1. 你的角色

- 你是唯一 Admin；同事是 **Write**（能推分支、开 PR、评论，不能动仓库设置）
- 你管三件事：人（协作者）、规则（分支保护）、密钥（`.env` / 服务器）

## 2. 协作者管理

**添加**：`Settings → Collaborators → Add people`，输入同事的 GitHub 用户名或邮箱，选 Write。

- 公开仓库对协作者数量没有限制
- 同事加入后自己会 `clone`，不需要你代劳

**移除**：同一页面 Remove。同事离职时记得移除，并确认他的本地副本/服务器不再使用。

**团队变大（>5 人）**：考虑把仓库迁入 GitHub Organization。公开仓库在组织下分支保护同样免费，管理更规整。

## 3. 分支保护（已生效）

公开仓库下，分支保护免费且强制。你现在已配置：

- 必须通过 PR 才能合并
- 至少 1 人 approve
- 代码改动后旧 approve 作废（dismiss stale）

建议再补充（`Settings → Branches`）：

- 禁止 force push 到 main（允许在功能分支上）——已完成
- CI 硬门禁：工作流已入库（`.github/workflows/test.yml`），PR 和 main 推送自动跑全量单元测试。还差最后一步网页操作：编辑 main 规则 → 勾选 **Require status checks to pass before merging** → 搜索选中 `Tests / pytest`

效果：**任何人（包括你自己）都无法直接推 main**，想改动只能走 PR。你自己日常开发照旧用 `codex/*` 分支再提 PR。

## 4. AI 协作时代，把关要点变了

同事大概率用 AI 写代码和推送。git 流程不变，但 AI 带来的风险比人更隐蔽，要额外设防：

1. **把 CI 变成硬门禁**：AI 声称"测试过了"不可信。CI 工作流已配好（`.github/workflows/test.yml`），PR 和 main 推送会自动跑 `pytest`。去分支保护里勾选 required status checks（选中 `Tests / pytest`）——机器没跑绿，合并按钮就是灰的，谁都绕不过。
2. **要求提交可追溯**：让每个同事配置 `user.name` / `user.email` 为真实身份，否则出问题不知道是哪次提交、哪个人（哪个 AI）干的。
3. **Review 时重点盯 AI 幻觉**：AI 的 PR 描述可能夸大（说"修复了 X"其实没修）、diff 可能夹带无关改动、可能谎称测试通过。合并前手动核对：diff 与描述一致、测试输出真实、无 `.env` / `*.db` / 密钥。
4. **密钥风险升级**：AI 可能在改代码时把 `.env` 里的 key 顺手写进新文件或 PR 描述。靠 GitHub secret scanning + review 双保险，收到警报立即轮换。
5. **冲突会变多**：多个 AI 并行改同一批文件时冲突概率高。让同事开工前 `git pull`、push 被拒就 rebase；你帮他们解决冲突时只动他们自己的分支。
6. **AGENTS.md 就是给 AI 看的**：AI 工具会自动读根目录 `AGENTS.md`，它就是项目的"AI 协作合同"。提醒同事用 AI 干活前先让它读一遍。

## 5. 每日维护流程

1. **看 Issues**：新 Issue → 打标签（`bug` / `enhancement`）→ 设优先级（P0 线上挂/数据安全，P1 功能问题，P2 改进）→ 指派（Assignees）或标 `good first issue` 给新人
2. **看 PR 列表**：有等待 review 的 PR 就看；要求描述里贴测试结果
3. **Review**：用 GitHub 的 review 功能，明确选 approve / request changes / comment
4. **合并**：推荐 **Squash merge**（一个 PR 压成一条提交，main 历史干净）；合并后点删除分支
5. **发布**：攒一批功能后打 tag（如 `v0.4.0`）+ 写 Release notes

## 6. Review 检查清单（每次合并前过一遍）

- [ ] diff 只包含 PR 描述里说的内容？无关改动要求拆出去
- [ ] 没有 `.env`、`*.db`、密钥、真实手机号混入？
- [ ] 测试结果：`pytest` 全绿？涉及知识库的 eval 全过？
- [ ] 符合项目约定：新功能新建文件、公共函数有类型注解、错误处理到位（见 `AGENTS.md`）
- [ ] 日志/报错不会泄露敏感信息

## 7. 帮同事解决冲突（他们搞不定时）

```bash
# 把同事的分支拉到本地，基于最新 main 重放
git fetch origin
git checkout -b 同事的分支 origin/同事的分支
git rebase origin/main
# 解决冲突：git add 文件 && git rebase --continue
git push --force-with-lease origin 同事的分支
```

推回去后让同事本地同步：

```bash
git fetch origin
git checkout 同事的分支
git reset --hard origin/同事的分支
```

## 8. 密钥与安全（最重要）

- 公开仓库的 **secret scanning 自动开启**：GitHub 会扫描提交里的已知密钥格式并发警报。收到警报 → **立即轮换**对应 key（本地 `.env`、服务器 `.env`、系统环境变量全部换）
- Review 时盯着有没有密钥混进 PR
- hermes 服务器：`.env` 单独维护，部署时只 `git pull`，**不要用本地 `.env` 覆盖服务器**
- 白名单：`whitelist.db` 不入仓。同事要测试号就加在线上库，**别把真实号码提交进仓库**
- 万一真实 key 已进公开仓库：先轮换（别先删历史），轮换完再考虑要不要清历史（公开仓库强推重写历史要非常谨慎，通常不值得）

## 9. 测试与质量门禁

```bash
cd backend && pytest tests/ -q                    # 257 项单元测试
python scripts/run_eval.py --phone 13985000001    # RAG 104 题评测（涉及知识库必跑）
```

- 自己改代码或合并前：必须全绿
- 涉及知识库（QA 字段、检索、提示词）：额外跑 eval
- 纯文档改动可以跳过
- 全绿才算完，这是项目铁律

## 10. 知识库变更治理

- 同事改知识库 → 要求走 `kb-update-workflow` 五阶段流程（源文档 → markdown → Q&A 抽取 → 查重 → 审核入库），别让他们直接改 `faq.json` 了事
- 每年 12 月制度变更 → 走 `regulations-migrate` skill 全链路（migration_map → 迁移 → 验证 → eval）
- 每条 QA 必须有 `source`、`category`、`indicators`；不确定的答案宁可不录
- 改完必跑：`python scripts/validate_faq.py`

## 11. 发布与服务器

发布流程建议：

1. 功能合并完，本地 `pytest` + eval 全绿
2. 打 tag：`git tag v0.4.0 && git push origin v0.4.0`
3. 写 Release notes（列新增/修复/注意点）
4. hermes 服务器：`cd /opt/labor-survey-ai && git pull` → 重启服务

hermes 上的 SSH 部署密钥**保持有效**（公开仓库也能用），别删。如果哪天换了服务器，在新服务器上重新生成密钥、重新加到仓库 Deploy keys。

## 12. 团队运转建议

- 保持"至少 1 人 approve 才能合并"（已配），不要自己破例
- 固定一个 review 搭档，互相看代码，比一个人把关靠谱
- 每周/每迭代花 10 分钟过一遍：待办 Issue、卡住的 PR、下一步方向
- 新同事入职：让他先读 `docs/协作手册-同事版.md`

## 13. 常见问题速查

| 现象 | 处理 |
|------|------|
| PR 合并按钮是灰的 | 原因一般是冲突 / 过时 approve / CI 红；解决冲突或让作者 rebase 后重新 review |
| 同事 push 被拒 | 教他 `git pull --rebase origin main` 再 push |
| 同事提交了 `.env` / `.db` | 不合并；让作者移除并确认没有真实密钥（有就轮换） |
| 收到 GitHub 密钥警报 | 立即轮换，优先级最高 |
| 同事想直接改知识库 | 引导走 kb-update-workflow，禁止绕过 |
