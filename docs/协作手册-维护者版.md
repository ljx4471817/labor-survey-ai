# 协作手册 · 维护者版（故事集）

> 主角**老张**就是你，AI 助手叫**小智**。六个故事覆盖你的全部日常。

## 故事一：老张开家门

小王发来 GitHub 用户名。老张打开仓库 → **Settings** → 左侧 **Collaborators** → **Add people** → 输入用户名 → 权限 **Write** → 发邀请。

"Write 就够了，"老张想，"能干活，动不了我的家。"

## 故事二：老张的独角戏（自批自合，会持续很久）

老张做了个功能：让小智开分支、写码、跑测试、推送、给 PR 链接。他点开链接，点 **Create pull request**，去泡了杯茶。

回来看到绿勾 **All checks have passed**。他没急着合，先点 **Files changed** 扫一遍：diff 和描述一致，没夹带私货，没碰 `.env`。

回到 Conversation 区往下滚，红字提示 **Review required**。老张熟练地勾上 **Merge without waiting for requirements to be met (bypass rules)**——作者不能自批，这是管理员特批的特权按钮。

蓝色按钮变成 **Bypass rules and merge**，点。弹确认，点 **Confirm merge**。紫色横幅 Merged 出现，点右下 **Delete branch**。

最后对小智说："切回主干，同步最新，删掉本地旧分支。"

小智提醒："小改动可以在 PR 页打开 **Enable auto-merge**——绿了自动合，你连按钮都不用点。重要的改动还是自己过一眼。"

> 口袋卡（六步）：绿勾 → 扫 diff → 勾 bypass 框 → 点 Bypass rules and merge → Confirm merge → Delete branch。

## 故事三：老张当裁判

小王的第一个 PR 来了。老张点开 **Files changed** 逐行看，发现日期硬编码，点那行旁的 **+** 号留言。全看完，右上 **Review changes** → 写总评 → **Request changes** → **Submit review**。

小王改完重推，老张再来，这次选 **Approve**。合并按钮自动亮起，**不再需要勾特批框**——有人批准了作者以外的改动，规矩就满足了。

老张想到：从今天起，自己的 PR 也可以让小王批，再不用特批了。

## 故事四：凌晨两点的警报

手机震了：GitHub 密钥警报——有人往公开仓库提交了疑似 API key 的字符串。

老张坐起来，先做最要紧的事：**轮换**。废掉旧 key、生成新 key，本地 `.env`、服务器 `.env`、系统环境变量三处全更新。做完才查是谁提交的——一个被 AI 带进新文件的测试 key。

早上他把这条写进同事版手册的红线，并在群里说："轮换完成，损失为零。下次先想后提交。"

> 顺序不能反：先轮换，后查原因，最后复盘。

## 故事五：老张给项目过生日

功能攒得差不多了。老张打开仓库右侧 **Releases** → **Draft a new release** → **Choose a tag** 输入 v0.4.0 → 填更新说明 → **Publish release**。

然后登录 hermes，说："拉最新代码，重启服务。"几十秒后线上就是新版。那把只读的 SSH 钥匙安静地待在服务器上，谁也没动它。

## 故事六：老张的十分钟巡视

每周五下午十分钟：给新 Issue 打标签、看有没有 PR 卡了三天、瞄一眼知识库队列、把下周最重要的一件事写成 Issue 指给小王。

"系统不会自己变好，"他对小智说，"但每周十分钟，它会一直好下去。"

## 附：老张的最后一页（规则备忘）

- main 有三把锁：必须 PR、必须 CI 绿、必须有人批准（自己的 PR 用特批框，见故事二）
- CI 绿勾在 PR 页 Conversation 区；红叉点开复制报错给小智
- 密钥警报 = 先轮换再查
- 公开仓库 = 全世界能看，红线清单常记
- hermes 的 SSH 钥匙：只读、只属于这个仓库、别删
