# 协作手册 · 维护者版

> 你（仓库拥有者）专用。核心三件事：**守住 main、管好密钥、让 PR 质量过关**。
> 本手册用自然语言描述：命令类操作全部交给 AI 执行，你只负责**对 AI 下指令**和**在网页上做决定**。

## 1. 你的角色

- 你是唯一 Admin；同事是 Write（能推分支、开 PR、评论、互相批，动不了仓库设置）
- 你管三样：人（协作者）、规则（分支保护）、密钥（.env / 服务器）

## 2. 协作者管理（网页点击）

**添加**：仓库 → **Settings** → 左侧 **Collaborators** → **Add people** → 输入对方用户名或邮箱 → 权限选 **Write** → 发邀请。对方接受后生效。

**移除**：同一页面找到人 → Remove。同事离职时记得移除。

## 3. 分支保护现状（已生效，别动坏）

路径备忘：仓库 → **Settings** → **Branches** → main 那条规则 → 铅笔编辑。

当前已开启：

- 必须走 PR 才能合并，至少 1 个批准
- 改动后旧批准作废（dismiss stale approvals）
- 禁止强推、禁止删除 main
- 管理员也受约束（连你自己也不能直接推 main）
- **必须通过 CI 检查才能合并**（required status check：Tests / pytest）

## 4. 当前阶段：你批你自己的日子（会持续很长时间）

现实：绝大多数 PR 是你提的、也由你合。GitHub 规定**作者不能批准自己的 PR**，所以你的标准动作是「管理员特批」。下面这套点击路径容易忘，记牢：

### 4.1 每个自有 PR 的合并流程（六步）

1. 打开 PR 页面，确认 Conversation 区是绿勾 **All checks have passed**
2. 点 **Files changed** 扫一眼全部改动：diff 和描述一致？没夹带无关文件？没碰 `.env` / `.db` / 密钥？（**特批前必做，别盲合**）
3. 回到 Conversation 区，往下滚到合并区，勾选 **Merge without waiting for requirements to be met (bypass rules)**
4. 蓝色按钮变为 **Bypass rules and merge** → 点它
5. 弹出确认就点 **Confirm merge**
6. 出现紫色横幅 "Merged" 后，点右下 **Delete branch** 清理分支

合并完成后，对 AI 说：「切回主干，同步最新代码，删掉本地旧分支」。

### 4.2 省事开关：自动合并

自己的 PR 创建后，在 Conversation 区合并按钮附近找到 **Enable auto-merge** 打开。之后只要 CI 绿、条件满足，GitHub **自动完成合并**，不用你守着页面。适合改动小、把握大的 PR；重要改动还是走 4.1 人工过一眼再合。

### 4.3 批同事的 PR（有同事之后）

1. 打开对方的 PR → **Files changed** → 逐块看，有问题点行号旁的 + 号留行内评论
2. 点右上 **Review changes** → 写总评 → 选 **Approve**（放行）或 **Request changes**（打回）→ **Submit review**
3. 批准后点合并按钮即可，**不再需要勾特批框**

同理，你自己的 PR 从此可以正常等同事批准，不勾特批框。

## 5. AI 协作时代的把关要点

1. **CI 硬门禁已生效**：AI 声称「测试过了」不算数，机器没跑绿合并按钮是灰的。你 review 时仍要核对 diff 与描述一致、测试输出真实
2. **提交可追溯**：确认同事的 AI 已把提交身份配成本人
3. **盯 AI 幻觉**：夸大描述、夹带无关改动、谎报测试，合并前手动核对
4. **密钥风险升级**：AI 可能把 `.env` 的 key 写进新文件或 PR 描述；GitHub 密钥扫描 + 你 review 双保险，收到警报立即轮换
5. **冲突会变多**：多 AI 并行时，让同事开工先同步、被拒就重放；你帮收尾时只动他们自己的分支
6. **AGENTS.md 是给 AI 看的合同**：同事用 AI 干活前让它先读

## 6. Review 检查清单（每次合并前过一遍）

- [ ] diff 只包含 PR 描述说的内容？
- [ ] 没有 `.env`、`.db`、密钥、真实手机号混入？
- [ ] CI 绿灯是真的（点开 Checks 看过）？
- [ ] 符合项目约定：新功能新建文件、类型注解、错误处理（AGENTS.md）
- [ ] 日志/报错不泄露敏感信息

## 7. 帮同事解决冲突

对 AI 说：「把同事的分支同步到最新主干，重放他的改动，冲突处理完列给我确认」。你确认每处保留哪边后，让它推送回同事的分支。**只动同事的分支，永远不直接动 main。**

## 8. 密钥与安全（最重要）

- GitHub 对公开仓库自动做密钥扫描：收到警报 → **立即轮换**对应 key（本地、服务器、环境变量全换），这是最高优先级
- hermes 服务器的 `.env` 单独维护；部署只拉代码，不用本地 `.env` 覆盖服务器
- `whitelist.db` 不入仓；同事要测试号就加在线上库，别提交真实号码
- 万一真实 key 已进公开仓库：先轮换，再考虑清历史（通常不值得）

## 9. 测试与质量门禁

- 全量单元测试：对 AI 说「跑全量测试」，全绿是底线
- RAG 评测（104 题）：知识库相关改动必跑，涉及 API key 所以不在 CI 里，由你在本地让 AI 跑
- 纯文档改动可跳过

## 10. 知识库变更治理

- 同事改知识库 → 引导走 kb-update-workflow 五阶段流程，禁止直接改 faq.json 了事
- 每年 12 月制度变更 → 走 regulations-migrate 全链路
- 每条 QA 必须有 source、category、indicators；不确定的宁可不录

## 11. 发布与服务器

1. 功能攒够、全绿后打版本：仓库页右侧 **Releases** → **Draft a new release** → **Choose a tag** 输入新版本号（如 v0.4.0）→ 填更新说明 → **Publish release**（发布时自动创建 tag）
2. hermes 部署：登录服务器，让 AI（或手动）拉取最新代码并重启服务
3. hermes 的 SSH 部署密钥保持有效，别删

## 12. 团队运转建议

- 保持「至少 1 人批准」，别自己破例；特批框是你独有的管理员权力，用前过 checklist
- 和固定搭档互相 review，比一个人把关靠谱
- 每周花 10 分钟过一遍：待办 Issue、卡住的 PR、下一步方向
- 新同事入职：先读同事版手册

## 13. 常见问题速查

| 现象 | 处理 |
|------|------|
| 自己的 PR 合并按钮灰的 | 正常——勾特批框（见 4.1 第 3 步），确认 CI 绿后再合 |
| 同事的 PR 合并按钮灰的 | 看缺什么：CI 红？没批准？有冲突？对应解决后自动解锁 |
| 同事推送被拒 | 让他同步主干重放（见同事版手册第 9 节） |
| 同事提交了 .env / .db | 不合并；确认无真实密钥后让他移除（有就轮换） |
| 收到 GitHub 密钥警报 | 立即轮换，最高优先级 |
| 同事想直接改知识库 | 引导走 kb-update-workflow，禁止绕过 |
