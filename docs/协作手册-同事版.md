# 协作手册 · 同事版

> 给参与共同开发的同事。先通读一遍，约 10 分钟；操作细节不用背，用到时回来查。
> 项目：劳动力调查 AI 助手（H5 + FastAPI + RAG 知识库）
> 仓库：<https://github.com/ljx4471817/labor-survey-ai>
>
> 本手册全部用自然语言描述。所有命令类操作都交给 AI（Codex 等）执行，你只需要知道两件事：**对 AI 说什么**、**在网页上点什么**。

## 1. 项目是干什么的

为辅助调查员提供基于 RAG 的即时填报指导：H5 前端 + FastAPI 后端 + 知识库检索（向量 + BM25 双轨）+ 手机号白名单鉴权。

## 2. 加入协作

1. 注册 GitHub 账号
2. 把**用户名**发给维护者（不要发密码）
3. 维护者在仓库设置里把你加为协作者（Write 权限）
4. 加入之前你也可以看代码、提 Issue、用 Fork 方式提 PR；加入之后才能直接推自己的分支

## 3. 第一次环境搭建

对 AI 说：

> 克隆仓库 ljx4471817/labor-survey-ai，安装后端依赖，参照根目录的 .env.example 生成 .env 文件，然后重建知识库索引，最后启动本地开发服务。

你只需要亲手做两件事：

- 打开 `.env` 文件，填入**你自己的** API key（申请入口见模板注释），并设置系统管理员手机号
- 把 GitHub 用户名发给维护者

**密钥纪律**：`.env` 只存在于你本地；不提交、不发聊天群、不贴进 Issue/PR。key 疑似泄露立即告诉维护者轮换。

**登录说明**：登录需要手机号在白名单里。本地没有白名单数据库时找维护者要一份开发库，或让维护者把你的测试号加进线上白名单。

## 4. 日常流程（每次都一样）

整段流程你对 AI 说的原话大概是：

1. 开工：「同步主干，开一条新分支，名字用 我的名字/功能说明」
2. 干活：「实现 XX 功能，补上单元测试，跑全量测试给我看结果」
3. 存档：「把这次改动提交，提交说明写 fix: 修复 XX」
4. 上传：「推送到 GitHub，然后帮我开 PR」

推送完 AI 会给你一个 PR 链接，后续都在网页上（见下一节）。

## 5. GitHub 网页点击详解（重点，容易忘）

### 5.1 打开 PR（如果没有自动跳转）

仓库首页 → 顶部 **Pull requests** → 绿色按钮 **New pull request** → 确认 base 选 `main`、compare 选你自己的分支 → **Create pull request** → 填标题和说明（改了什么 / 为什么改 / 怎么验证的）→ 再点 **Create pull request**。

### 5.2 看 CI 机器人检查

PR 页面下方会自动出现检查区：

- **绿色对勾 All checks have passed** → 通过，等维护者批
- **红色 All checks have failed** → 点开失败的那条 → 找红色报错文字 → 整段复制发给 AI，说「修好重新推送」→ AI 推送后 PR **自动更新、自动重跑**，不要重新开 PR

### 5.3 收到修改意见后

PR 页面 → **Files changed** 标签 → 看每条评论 → 让 AI 按意见修改并推送到**同一条分支** → PR 自动带上新提交，评论旁会显示状态。

### 5.4 批别人的 PR（review）

打开对方的 PR → **Files changed** 标签 → 逐块看改动 → 点右上角 **Review changes** → 写一句总评 → 选 **Approve**（同意）或 **Request changes**（需要改）→ **Submit review**。

### 5.5 讨论

PR 页底部评论框直接留言，@ 对方用户名可以点名提醒。

## 6. 合并（维护者操作，同事了解即可）

CI 绿 + 维护者批准后，由维护者在 PR 页点合并。当前阶段维护者自己提的 PR 自己合，会走一个「管理员特批」勾选框——那是维护者手册的事，同事不用管。

## 7. 用 AI 协作的补充规矩（重要）

1. **让 AI 认人**：先让它把 git 用户名/邮箱配成你的真实身份，提交才能追溯到人
2. **别让 AI 一把梭**：明确要求只提交本次相关文件，不动 `.env`、`.db`、密钥，不顺手格式化无关代码
3. **要求贴真实验证结果**：AI 声称「测试过了」不算数，让它在 PR 里贴实际运行输出
4. **推送被拒就重放**：告诉 AI「远端有新提交，同步后重推」，并强调**永远不要强行覆盖别人的分支或 main**
5. **开工先同步**：每次让 AI 干活前先同步主干，别基于过期代码改
6. **AI 报错不是完工**：让 AI 处理完报错、测试全绿再提 PR

根目录的 `AGENTS.md` 是 AI 工具自动读取的项目约定，开工前让 AI 先读它。

## 8. 分支保护（main 推不上去是正常的）

main 已上锁：不能直接推送，改动必须走 PR；PR 的代码被改过之后旧批准作废、需要重新批。你直接往 main 推会被拒绝——这不是故障，是规矩在起作用。

## 9. 冲突（两个人改了同一处）

现象：推送被拒。解决：对 AI 说「同步主干，把我的改动重放上去，有冲突就标出来」。AI 处理完冲突标记后，**你负责逐处确认保留哪边**（别漏掉任何一方），确认后让它继续推送。

## 10. 质量门禁

| 改动类型 | 合并前必须满足 |
|---------|--------------|
| 改代码 | 全量单元测试全绿（对 AI 说「跑全量测试」，把结果贴进 PR 描述） |
| 改知识库 | 先让 AI 跑知识库字段校验；104 题评测由维护者跑 |
| 新功能 | 遵守项目分层规范（AI 会读 AGENTS.md 自动遵守） |

提交 PR 后 GitHub 还会自动再跑一遍 CI，绿灯是合并前提。

## 11. 红线（违反会出事）

1. **绝不提交** `.env`、任何 `.db` 文件、API 密钥、真实手机号数据
2. 真实 key 不发聊天群、不贴 Issue/PR
3. 仓库是**公开**的——不提交内部敏感文档、制度原文截图、个人数据
4. 不直接推 main
5. 发现 key 疑似泄露 → **立刻**告诉维护者
6. 动数据库结构、删除历史、改部署配置 → **先问维护者**

## 12. 提 Issue（报 bug / 提需求）

仓库首页 → 顶部 **Issues** → 绿色 **New issue** → 选模板（bug / 功能建议）→ 标题一句话，正文写清：现象、复现步骤、期望结果、截图/日志 → 选标签（bug / enhancement）→ **Submit new issue**。

你的 PR 修好了某个 Issue 的话，在 PR 描述里写「Closes #编号」，合并时 Issue 自动关闭。

## 13. 遇到问题找谁

- 环境搭不起来 / 登录不了 → 维护者
- 不熟悉某块代码 → 先看 `docs/03-架构设计.md`、`docs/04-知识库规范.md`
- 想改知识库内容 → 先和维护者对需求，知识库有专门流程
