# 协作手册 · 同事版

> 给参与共同开发的同事。先读这一份，约 10 分钟。
> 项目：劳动力调查 AI 助手（H5 + FastAPI + RAG 知识库）
> 仓库：<https://github.com/ljx4471817/labor-survey-ai>

## 1. 项目是干什么的

为辅助调查员提供基于 RAG 的即时填报指导：H5 前端 + FastAPI 后端 + 知识库检索（向量 + BM25 双轨）+ 手机号白名单鉴权。

## 2. 加入协作

1. 注册 GitHub 账号
2. 把**用户名**发给维护者（不要发密码）
3. 维护者在仓库 `Settings → Collaborators` 把你加为 **Write** 权限
4. 加之前你可以看代码、提 Issue、提 PR（Fork 方式），但推送分支要等加入

## 3. 第一次环境搭建（约 20 分钟）

```bash
# 克隆
git clone https://github.com/ljx4471817/labor-survey-ai.git
cd labor-survey-ai

# 安装后端依赖
cd backend
pip install -r requirements.txt
cd ..

# 配置环境变量（把模板复制成 .env 再编辑）
cp .env.example .env          # Windows 用：copy .env.example .env
# 编辑 .env，填入 DEEPSEEK_API_KEY、DASHSCOPE_API_KEY，
# 并把 LSX_SYSTEM_ADMIN_PHONE 设成你自己的手机号

# 首次构建知识库（向量 + BM25，必跑）
python scripts/rebuild_all.py

# 启动开发后端
cd backend
uvicorn app.main:app --reload --port 8001
# 浏览器打开 http://localhost:8001/
```

**登录说明**：登录需要手机号在白名单里。本地开发若没有 `backend/data/whitelist.db`，找维护者要一份开发库，或让维护者把你的测试号加进线上白名单。

**密钥纪律**：`.env` 只在你本地存在，绝不提交、不发给任何人、不贴到聊天群和 Issue/PR 里。key 丢了/泄露了立即告诉维护者轮换。

## 4. 日常协作流程（核心，每次都要走）

```bash
# 1) 开工前：同步主干
git checkout main
git pull

# 2) 开自己的功能分支（建议格式：名字/功能，避免和别人撞名）
git checkout -b zhangsan/fix-login

# 3) 改代码 → 小步提交（提交信息格式见下）
git add .
git commit -m "fix: 修复登录页按钮错位"

# 4) 推送到远端
git push -u origin zhangsan/fix-login
```

推送完，终端会输出一个链接，打开就是 **Pull Request（PR）** 页面。按模板填清楚：

- 改了什么
- 为什么改
- 怎么验证的（贴测试结果）
- 关联的 Issue（写 `Closes #12` 合并时自动关闭）

然后 @ 维护者来 review。收到修改意见就继续改、继续 `git push` 同一分支，PR 会自动更新，**不要重开 PR**。合并由维护者完成，合并后删掉你的分支。

**提交信息格式**（仓库统一约定）：

```
feat: 新功能
fix: 修 bug
refactor: 重构
docs: 文档
test: 测试
chore: 杂项
```

例如：`fix: 修复会话列表刷新后丢失的问题`。

## 5. 用 AI 协作的补充规矩（重要）

大家都用 AI 写代码和推送，git 底层流程不变（AI 也是开分支、commit、push、提 PR），但要额外守这几条，否则 AI 的"手滑"比人更隐蔽：

1. **先让 AI 认人**：在本地配置一次 git 身份，提交才能追溯到人：

   ```bash
   git config --global user.name "你的真实姓名"
   git config --global user.email "你的GitHub邮箱"
   ```

2. **别让 AI 一把梭**：明确要求 AI 只提交本次改动相关的文件，不要 `git add .`、不要顺手格式化无关文件、不要动 `.env` / `*.db` / 密钥。`.gitignore` 挡得住大部分，但挡不住 AI 把 key 写进新文件或 PR 描述。
3. **要求 AI 贴真实验证结果**：AI 经常声称"测试已通过"但根本没跑。改完让 AI 在 PR 里贴 `pytest` 的实际输出（或你确认它跑了）；涉及知识库的改动由维护者跑 eval。合并前的最后闸门是维护者的 review，不是 AI 的自述。
4. **push 被拒就让 AI 先 rebase**：多个 AI 同时干活冲突会变多。让 AI 用 `git pull --rebase origin main` 再 `git push --force-with-lease`，并明确告诉它**永远不要 force push 到别人的分支或 main**。
5. **开工前先同步**：每次让 AI 干活前先 `git pull`，别让它基于过期代码改。
6. **AI 报错时让它先自查**：工具报错不是代码完成信号，让 AI 把报错处理完、测试跑绿再提 PR。

另外，根目录的 `AGENTS.md` 就是给 AI 工具看的项目约定，AI 会自动读取，改代码前让它先读一遍。

## 6. 分支保护（已开启，别慌）

仓库已开启保护：**main 不能直接推送**，任何改动必须走 PR 且至少 1 人 approve。

- 你直接 `git push` 到 main 会被 GitHub 拒绝——这是正常的，说明规则在起作用，走 PR 即可
- PR 里的代码被 review 改过之后，旧的 approve 会作废，需要重新 approve——这也是正常的

## 7. 同步与解决冲突

**push 被拒**（远端主干有新提交）：

```bash
git pull --rebase origin main
```

如果提示 `CONFLICT`，打开冲突文件，里面是：

```
<<<<<<< HEAD
你的代码
=======
别人的代码
>>>>>>> origin/main
```

把中间改成最终要保留的样子（别丢掉任何一方），删掉 `<<<<<<<`、`=======`、`>>>>>>>` 标记行，然后：

```bash
git add 冲突文件
git rebase --continue
git push --force-with-lease
```

`--force-with-lease` 是安全的强推方式，只允许在**自己的分支**上用，永远不要对 main 用。

## 8. 质量门禁（合并前必须满足）

| 改动类型 | 必须做的事 |
|---------|-----------|
| 改代码 | `cd backend && pytest tests/ -q` 全绿（257 项） |
| 改知识库（`knowledge-base/qa/faq.json` 等） | 先跑 `python scripts/validate_faq.py`；eval（104 题）通常由维护者跑 |
| 新增功能 | 遵守项目分层规范（见 `AGENTS.md`）：路由放 `backend/app/api/`、逻辑放 `services/`、纯函数必须带单测 |

PR 描述里把测试结果贴出来，维护者看到绿了才会合并。

提交 PR 后，GitHub 会自动触发 CI（任务名 `Tests / pytest`）跑全量测试；CI 绿灯是合并的前提。本地先跑一遍再提 PR，能省一轮返工。

## 9. 红线（违反会出事，请务必遵守）

1. **绝不提交** `.env`、`*.db`、任何 API 密钥、真实手机号数据（`.gitignore` 已挡，但不要绕过它）
2. 真实 API key **不**发聊天群、不贴 Issue/PR
3. 仓库是**公开**的——不提交内部敏感文档、制度原文截图、个人数据
4. 不直接 push main
5. 发现密钥疑似泄露 → **立刻**告诉维护者（需要轮换）
6. 数据库 schema 变更、删除历史、动 `.env`/部署配置 → **先问维护者**

## 10. 提 Issue 的规范

- bug 和需求都走 Issue，选标签（`bug` / `enhancement`）
- 写清楚：现象、复现步骤、期望结果、截图/日志
- PR 关联 Issue：描述里写 `Closes #编号`

## 11. 命令速查表

| 想做什么 | 命令 |
|---------|------|
| 开工前同步 | `git checkout main && git pull` |
| 开分支 | `git checkout -b 名字/功能` |
| 推送分支 | `git push -u origin 分支名` |
| 同步主干并重放自己的提交 | `git pull --rebase origin main` |
| 冲突后继续 | `git add 文件 && git rebase --continue` |
| 重新推送自己的分支 | `git push --force-with-lease` |
| 跑测试 | `cd backend && pytest tests/ -q` |
| 校验知识库字段 | `python scripts/validate_faq.py` |
| 重建知识库 | `python scripts/rebuild_all.py` |

## 12. 遇到问题找谁

- 环境搭不起来 / 登录不了 → 维护者
- 不会改某块代码 → 先看 `docs/03-架构设计.md` 和 `docs/04-知识库规范.md`
- 想改知识库内容 → 先跟维护者对一下需求，知识库有专门流程

详细项目约定见仓库根目录 `AGENTS.md`。
