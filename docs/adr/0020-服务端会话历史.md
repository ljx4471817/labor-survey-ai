# 0020 · 服务端会话历史

## 背景

原 H5 只在页面内存中保留最近 4 轮对话，刷新后上下文消失，也无法回看历史。用户需要在手机端继续旧对话并查看之前问答。已有 `query_log` 只记录问题与检索元数据，不保存答案与来源，不适合作为用户历史会话的唯一数据源。

## 决策

1. **服务端永久保存会话**。新增 `conversations` 和 `conversation_messages` 两张表，历史按当前登录手机号隔离。
2. **首次成功回答时创建会话**。点「新对话」只重置前端；第一次成功返回助手回复时才创建会话，标题取第一句提问前 20 个字符。
3. **回答模式全量保存**。`rag`、`out_of_kb`、`out_of_scope`、`ambiguous` 均写入会话；接口失败或 LLM 异常的轮次不入库。
4. **保存来源快照**。RAG 回答的 QA 编号、标准问法、来源、分类、分数与图片路径写入 `sources_json`，历史回看展示当时的依据。
5. **历史 UI 只看最近 10 轮**。历史列表默认 10 个会话并支持加载更多；打开单个会话只加载最近 10 轮（20 条消息），第一版不提供更早消息分页、搜索或重命名。
6. **LLM 上下文限流**。服务端从会话库读取最近 8 条消息（约 4 轮）生成回答，不信任前端传入的历史。旧 API 在未传 `conversation_id` 时继续兼容请求内 `history`。
7. **用户删除采用物理删除**。删除会话与其消息；`feedback.jsonl` 和 `query_log` 不删除，反馈复核与用量/热点统计不中断。
8. **管理端不查看完整用户会话**。历史只能由当前登录手机号读取；管理端不提供完整聊天审计。
9. **多端不同步实时消息**。切换或刷新时拉取最新 10 轮，第一版不做轮询或 WebSocket。

## 后果

- 用户可以跨设备继续旧会话，手机端历史入口保持轻量。
- `conversation_messages` 会长期增长，后续若性能或存储成为问题，需单独评估归档策略。
- 用户删除后，反馈记录仍可能保存其反馈时提交的问题和答案；这是反馈追溯闭环的刻意保留。
- `query_log` 与用户可见历史语义分离：前者服务统计与 KB 改进，后者服务用户上下文。
