# ADR 0013 — RAG 规则冲突裁决（F27 装修工月收入矛盾修复）

> 状态：已采纳（2026-08-10）
> 触发：同一 query 两次 RAG 返回相反结论（一次「不折算」、一次「应折算」），用户截图投诉。
> 决策者：开发者（数据分析 + prompt 调优）

## 背景

KB 中存在多条制度条款，它们的**触发词高度重叠、适用场景边界模糊、结论互相排斥**。

典型案例（触发本次修复的 F27 冲突）：
- aq.id=058：「F27 税前还是税后」——把「上月应得 ≠ 实得」和「年薪/不同周期应折算」合并在同一条，触发词宽。
- aq.id=237：「住户说收入大概怎么填」——兜底话术（「五六千填 5500」），「如果是按月发」措辞误导 LLM 把装修工也套入月薪逻辑。

对 query「装修工每月工资浮动大，月收入怎么填」，两条都被 RRF 检索召回，LLM 在上下文中对「应得 vs 折算」无优先级判断，随机裁成 A 或 B，导致同一 query 两次回答相反。

这不是 KB 内容错误，而是**规则层缺少冲突裁决机制**。

## 决策

**三层组合**解决，而不是只改 KB（避免 KB 越改越碎、越碎越容易新冲突）：

### 层级 1 — system prompt 加硬规则（最高杠杆）

ackend/app/rag/prompts.py 硬规则新增**第 7 条**「规则冲突裁决」：

1. 先判断**发放周期**：月薪/周薪等按月发放 → 适用「上月实际应得」条款，**不折算**；年薪、按项目、按季、按年或不同周期 → 适用「折算月平均」条款。
2. 再判断**住户是否配合**：住户已给具体金额 → 直接填报，不进入兜底流程；住户不肯说 → 才使用范围引导话术取中间值；实在不愿说才记「拒答」。
3. 估算兜底流程（取中间值 / 拒答）**永远不能替代**发放周期判断。
4. 装修工、建筑工、零工等灵活就业人员，**先问发放周期**。
5. 回答必须引用制度原文，不可凭空给出「应折算 / 不应折算」。

### 层级 2 — FAQ answer 加 scope 限定（精准收窄）

aq.id=237 answer 加前缀约束：「本条仅适用于月薪/月薪制工人，不适用于年薪制、按项目/按年/不同周期结算的灵活就业人员（这类人群应折算月平均，不进入本条估算流程）」。

意义：**KB 条目自带 anti_scope**，即使被误召回，LLM 看到「不适用」也会跳过。

### 层级 3 — eval 回归锁死（门禁）

eval_set.json 新增：
- eval-103：装修工 query → 必须追问发放周期 / 不输出「不要折算」「五六千填 5500」
- eval-104：月薪工 query → 必须答「实际应得」/ 不输出「折算月平均」

未来每次 prompt 改动，eval-103/104 作为硬门禁回归。

## 取舍

| 备选方案 | 为何不选 |
|---------|---------|
| 只改 KB（删 FAQ / 拆条目）| KB 越拆越碎，新条目反而制造新冲突；拆到 600 条后 BM25 召回噪声反而升高 |
| 改 retriever（加关键词白名单）| 关键词维护成本极高，且会引入新 bug（query 含「装修」反被错推折算）|
| 只改 prompt 不加 eval | prompt 改了但无法验证，下次改 prompt 又翻车 |

**当前组合是最小改动 + 最大杠杆**：prompt 改一处、FAQ 改一条、eval 加两条。

## 后果

- **正面**：装修工相关 query 收敛到「先问发放周期」；KB 不再需要为每种人群拆条目。
- **负面**：prompt 硬规则每新增一条都增加 LLM 推理负担；rule 7 有 F27 专属措辞（「装修工、建筑工、零工」），未来扩展到 F10/F11 需另写一条。
- **中性**：eval 集从 102 扩到 104，跑 eval 耗时增加约 2 条 DeepSeek 调用。
