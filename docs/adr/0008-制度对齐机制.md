# ADR 0008 — 制度对齐机制（KB schema v1）

> 状态：✅ 已采纳（2026-06-26）
> 触发：迭代 2 KB 质量优化阶段，需要把 KB 条目结构化关联到制度指标 F/H 编号，避免每年制度变更时手动排查几百条 QA。

## 背景

劳动力调查制度每年 12 月初发布新版（《劳动力调查制度（YYYY年定期报表）-定稿》），典型改动：3-10 个指标增/删/位移（如 2025 年 F26 → 2026 年 F25）。当前 KB 有 335 条 QA，正文里到处写着"F10 / F11 / F27"等指标编号，制度变更时需要：

1. 找出所有提到被影响指标的 QA 条目
2. 把正文里的旧编号改成新编号
3. 删掉不再适用的条目 / 重写
4. 重建 BM25 索引 + 跑全量回归确认未退化

这条链路过去完全靠人手 + grep + sed，每次制度变更耗时 1-2 小时且容易漏。本 ADR 把这条链路标准化。

## 决策

引入 **KB schema v1**：每条 QA 加 `indicators` 字段，结构化关联到制度指标；配套 `indicator_catalog.json`（权威指标目录）+ `migration_map.json`（变更映射）+ 三个脚本（回填、迁移、智能回填）+ `regulations-migrate` skill（流程封装）。

### Schema 变更（faq.json）

每条 QA 在原有 6 个字段基础上，新增两个**二选一**字段：

```json
{
  "id": "001",
  "category": "就业状态判断",
  "question": "...",
  "answer": "...",
  "source": "劳动力调查制度（2026版）第三章第二节·问题10",
  "keywords": ["..."],
  "indicators": ["F10", "F11"]   // 关联制度指标 F/H 编号（必须在 indicator_catalog.json 中）
  // 或
  "_indicators_topic": "入户沟通/调查技巧"  // 非指标类条目（程序/抽样/技巧/法规等）
}
```

**约束**：
- `indicators` 必须是 `indicator_catalog.json` 中已注册的 F/H 编号
- 程序/抽样/入户技巧/统计法等非指标类条目，用 `_indicators_topic` 字段（9 类枚举），不要硬塞 indicators
- 不确定时打 `_indicators_review: true`，跑 `smart_backfill_indicators.py` 兜底
- 改 faq.json 后必跑 `validate_faq.py`，未填 indicators 会被警告

### 三个脚本

| 脚本 | 用途 |
|------|------|
| `scripts/backfill_indicators.py` | 从 source/question/answer 正则提取 F/H 编号，置信度高的自动填 |
| `scripts/migrate_indicators.py` | 读 `migration_map.json`，把旧编号改新编号、同步 indicators 字段和正文 |
| `scripts/smart_backfill_indicators.py` | 关键词打分 + 人工覆盖规则，处理 review 条目（命中率 95%+） |

### indicator_catalog.json

权威指标目录，结构：

```json
{
  "version": "2026",
  "document": "劳动力调查制度（2026年定期报表）-定稿",
  "total_indicators": 63,
  "modules": {
    "住户信息":   {"H1": {...}, "H2": {...}, "H3": {...}},
    "个人信息":   {"F1": {...}, ..., "F9.3": {...}},
    "工作情况":   {"F10": {...}, ..., "F30.1": {...}},
    "无工作情况": {"F31": {...}, ..., "F41": {...}}
  }
}
```

63 个指标对应 2026 版制度。制度变更时，catalog 必须先更新（migration 脚本会自动同步），再迁移 faq.json。

### migration_map.json

制度变更时的人工编辑文件，schema：

```json
{
  "target_version": "2027",
  "date": "2026-12-XX",
  "renamed": {"F26": "F25"},
  "removed": ["F22.1"],
  "added": [{"code": "F42", "description": "...", "type": "单选"}]
}
```

### regulations-migrate skill

项目级 skill（`.codex/skills/regulations-migrate/SKILL.md`），封装整条 7 步链路：定位新制度 → 提取指标 → 比对 catalog → 生成 migration_map 草稿 → 用户审核 → 跑脚本 → 验证回归。用户只需提供新制度 markdown 所在目录，AI 接管其余步骤。

## 后果

### 优点
- **制度变更耗时从 1-2 小时降到 10 分钟**（跑 skill + 审 diff）
- **变更可追溯**：`git diff knowledge-base/migration_map.json` 看清每年改了什么
- **审计友好**：`indicators_unknown_code` 校验保证不会有未注册编号进入 faq.json
- **新人友好**：理解 KB 不再需要 grep，直接看 indicators 字段就知道每条关联什么指标

### 缺点
- 多 2 个字段（indicators / _indicators_topic），faq.json 体积增大约 5%
- 首次填充要跑脚本（一次性成本）
- `smart_backfill_indicators.py` 的关键词打分有边界 case，需要持续维护 `MANUAL_OVERRIDES` 字典

### 风险
- **过度依赖 migration_map.json**：如果 catalog 漏更新某个新指标，迁移后会出现"未知编号"。对策：catalog 必须每年先于 migration 改
- **关键词打分误判**：`score=1` 的低置信匹配易误标，脚本已用 `score ≥ 2` 阈值；仍有少数需要人工 review
