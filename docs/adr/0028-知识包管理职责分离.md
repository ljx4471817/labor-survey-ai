# 0028 — 知识包管理职责分离

日期：2026-10-23
状态：已采纳

## 背景

多知识包能力（ADR 0026 / 0027）落地后，`/kb-admin` 页面同时提供了「新建知识包」「登记版本」和「发布 / 回滚 / 省份绑定」两类操作。实际运行中发现：

1. 建包、登记版本是**内容生产决策**（按内容适用范围归类，ADR 0027），实际都在开发机由脚本完成；后台手工入口在正常流程中冗余，且是「绕过构建链路的假登记」风险入口（手工填 content_hash、手工标 eval passed）。
2. 项目当前及可预见周期内只有一名管理员（开发者本人），后台应当是「运营决策台」而不是「内容生产线」的第二个入口。
3. `build_release_index.py --register` 已实现构建成功后自动登记版本并绑定产物 manifest 的 canonical content hash，发布门禁对 hex 格式 hash 做强校验（409 拒绝不匹配），登记环节已可完全自动化。

## 决策

1. **后台 UI 只保留运营动作**：查看（包 / 版本 / 绑定 / 审计）、发布、回滚、省份绑定、停用 / 启用、检索预览。移除「新建知识包」「登记版本」两个表单。
2. **内容生产链路收敛到开发机**：改 KB → `split_knowledge_packs.py` → `build_release_index.py --register` → Eval 通过 → 回后台发布 / 绑定。
3. **`--register` 自动创建缺失的知识包**（按 pack manifest 的 kb_id / name / kind，draft 状态），新增省份的包记录不再依赖后台入口。
4. **后端 API 保留** `POST /kb/packages`、`POST /kb/packages/{id}/releases`（应急与脚本化用途），仅 UI 不再暴露；发布 / 回滚前的产物完整性与 content_hash 强校验不变。
5. `eval_status` 永远只能由人工在 Eval 实际通过后更新，任何自动流程不得标记 passed。

## 后果

- 正向：注册库数据与磁盘产物强绑定，假登记面收窄；后台操作面收敛为纯运营决策；新增省份全链路可在开发机一条命令闭环。
- 负向：应急场景下建包 / 登记需登开发机或直接调 API；页面不再能「一步建包」，对后续接手者是刻意设计的摩擦（见本 ADR）。
- 页面内置「操作指引（备忘）」卡片提示两条流程与关键注意事项，完整细节在 `docs/knowledge-packs.md`。
