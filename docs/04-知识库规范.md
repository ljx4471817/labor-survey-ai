# 知识库规范

## 一、目标

知识库是回答质量的决定因素。本规范约束 QA 的录入格式、分类法、来源标注，确保：
- 检索召回率最大化
- 答案可追溯到制度依据
- 离线模式可直接消费

---

## 二、QA 数据格式

### 2.1 JSON Schema

每条 QA 是 `knowledge-base/qa/faq.json` 数组中的一个对象：

```json
{
  "id": "001",
  "category": "就业状态判断",
  "question": "一个人每周工作15小时，算不算就业人口？",
  "answer": "根据劳动力调查制度，就业人口的判断标准是：在调查参考周内，从事1小时以上有收入的劳动即为就业。每周工作15小时当然属于就业人口。需要注意的是...",
  "source": "劳动力调查制度（2024版）第三章第二节",
  "keywords": ["就业", "工作时间", "15小时", "就业人口"]
}
```

### 2.2 字段说明

| 字段 | 必填 | 类型 | 说明 |
|------|------|------|------|
| `id` | ✅ | string | 唯一标识，3 位数字字符串（001, 002, ...） |
| `category` | ✅ | string | 一级分类（见第三节分类法） |
| `question` | ✅ | string | 调查员可能的提问方式，**口语化**（实际入户时的措辞） |
| `answer` | ✅ | string | 标准答案，**书面化**（引用制度依据） |
| `source` | ✅ | string | 答案引用的制度来源（章/节） |
| `keywords` | ✅ | string[] | 用于离线检索的关键词，至少 3 个 |

### 2.3 字段填写规则

#### `id`
- 3 位数字字符串（"001" 到 "999"）
- 顺序递增，不复用
- 扩展业务时加前缀：`H001`（住户调查）、`P001`（价格调查）

#### `category`
- 见第三节分类法
- 一条 QA 只属于一个一级分类

#### `question`
- 用调查员**实际可能问的方式**写
- 包含典型数字、案例（如"15小时"、"学生打工"）
- 多个常见问法可用多个 QA（id 不同）覆盖

✅ 好的例子：
- "一个人每周工作15小时，算不算就业人口？"
- "在校学生暑期打工算就业吗？"
- "退休人员返聘算就业吗？"

❌ 不好的例子：
- "请解释就业人口的定义。"（太学术）
- "就业人口判断标准"（不是问句）

#### `answer`
- **必须**基于制度文档，不编造
- 简洁、直接、可操作
- 涉及具体指标判断时引用制度章节
- 长度建议 100-300 字
- 结尾如有补充说明（如"需要注意的是..."），可加但不超过 50 字

✅ 好的例子：
> 根据劳动力调查制度，就业人口的判断标准是：在调查参考周内，从事 1 小时以上有收入的劳动即为就业。每周工作 15 小时当然属于就业人口。需要注意的是，"有收入"包括实物报酬，如免费食宿折算。

❌ 不好的例子：
> 就业人口是一个比较重要的概念。一般来说，如果一个人从事了劳动，那么就算就业。具体请参考相关制度。（无依据、太泛）

#### `source`
- 精确到章/节：`劳动力调查制度（2024版）第三章第二节`
- 多源时用分号分隔：`制度A第三章；制度B附录二`
- 无法追溯时填 `待核实`，**且不应入知识库**——核实后再录

#### `keywords`
- 至少 3 个
- 包含核心名词、典型数字、相关场景
- 用于离线 TF-IDF 检索，命中率比在线 embedding 低，需靠关键词补偿

✅ 好的例子：`["就业", "工作时间", "15小时", "就业人口", "在校学生"]`

❌ 不好的例子：`["就业"]`（太少）、`["就业人口怎么判断"]`（这是句子不是关键词）

## 三、分类法

一级分类（与离线 FAQ 页面分类一致）：

| 分类 | 范围 | 示例问题 |
|------|------|----------|
| 就业状态判断 | 就业/失业/不在劳动力的判断标准 | 就业人口定义、失业人口定义、退休算不算 |
| 工作时间 | 周工作小时数、加班、请假 | 15小时算就业吗、带薪假算工作时间吗 |
| 调查时点 | 参考周、调查周、登记时间 | 调查参考周是哪一周 |
| 调查对象 | 谁是劳动力调查对象 | 住户成员、外出人员、流动人口 |
| 行业职业 | 行业分类、职业分类 | 农民算什么行业、个体经营算什么 |
| 失业原因 | 失业的细分原因 | 季节性失业、被动失业、主动失业 |
| 填报规范 | 问卷填写规则 | 漏项怎么处理、涂改规则 |
| 编码规则 | 代码填写 | 行业代码、职业代码、原因代码 |
| 抽样方法 | 样本轮换、抽样框 | 户样本怎么抽、轮换周期 |
| 家庭关系 | 户主、配偶、子女判定 | 户主如何判定、外嫁女归属 |
| 收入相关 | 工资、经营收入、财产性收入 | 实物收入怎么折算、单位福利算不算 |
| 数据质量 | 核查、比对、异常处理 | 数据异常如何核实 |

**新增分类时**需更新：
1. `docs/04-知识库规范.md`（本文件）
2. `knowledge-base/qa/faq.json` 中已录入的 QA 同步重新分类
3. 后端 `GET /api/faq/categories` 接口返回新分类

## 四、录入流程

### 4.1 收集阶段

1. **原始素材**：从 `knowledge-base/raw/` 取制度文档
2. **问法采集**：从培训问答、调查员反馈、实际入户场景中提取
3. **答案整理**：从制度原文、培训资料中提取标准答案

### 4.2 录入阶段

1. 编辑 `knowledge-base/qa/faq.json`
2. 新 QA 加到数组末尾，id 递增
3. 每条 QA 必填字段都填，不留空
4. 来源追溯清楚，无法追溯的不录

### 4.3 验收阶段

每批录入后做：
1. **数量检查**：JSON 解析成功，字段完整
2. **检索测试**：用 5-10 个典型问题检索，Top-3 应包含预期 QA
3. **离线测试**：随机抽取 10 条验证离线模式正确展示

### 4.4 增量更新

新增 QA 不需要重建向量库——`scripts/build_kb.py` 应支持增量：

```bash
# 全量重建
python scripts/build_kb.py --full

# 增量（只处理新增/修改的 QA）
python scripts/build_kb.py --incremental
```

## 五、质量红线

下列情况**禁止**入知识库：

1. **无来源依据**：制度文档中找不到对应条款
2. **主观判断**：答案含"我认为"、"一般情况"等非制度性表述
3. **涉及居民个人信息**：哪怕是脱敏后的案例
4. **过时制度**：已被新制度替代的旧版答案
5. **与其他 QA 矛盾**：未与已有 QA 对齐口径

发现问题立即：
1. 删除该 QA
2. 在 `docs/04-知识库规范.md` 附录「变更日志」中记录
