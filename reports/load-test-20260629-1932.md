## 结论 / 瓶颈定位

### 关键观察

1. **0 错误率**：4 档全跑 0 个 5xx/4xx，**系统扛得住不崩**——这是发布会前的硬指标。
2. **拐点在 50 并发**：P50 从 3.3s → 4.2s（+27%），P95 从 4.9s → 6.4s（+30%），属线性劣化。
3. **100 并发已饱和**：QPS 11.12 ≈ 50 并发 11.17，**吞吐量零增长**——说明 uvicorn 单进程到了瓶颈。
4. **100 并发 P95 = 12.4s**：**用户体验已不可接受**（>30s 的判断依据：用户耐心阈值；6-10s 是可容忍上限）。

### 瓶颈定位

- **LLM 调用是延迟主因**：单条基线 3-4s（其中 embedding + Chroma < 1s，LLM 2-3s 占大头）。
- **uvicorn 单进程 + anyio 线程池（默认 40 token）+ ThreadPoolExecutor(4)**：三者上限叠加 → 50 并发开始排队。
- **Chroma SQLite 串行锁**：单 collection 单文件，>20 并发后写入/查询互锁，但本次压测主要是读，影响小于 LLM。
- **DashScope embedding 同步 HTTP**：未限速，但本次未触发 5xx（DeepSeek 默认 2500 RPM 也未触发）。

### 与发布会场景匹配度

300 调查员 × 月度高峰期 6 天 × 每天 6 小时：
- 平均 QPS ≈ 0.21，**远低于 50 并发拐点（11 QPS）**——日常流量完全无压力。
- 脉冲峰值（领导演示、月报启动首日）经验估算 50-80 并发 → **50 并发档 P95=6.4s 可接受**。
- 100 并发是真实的 2 倍安全冗余。

### 改进建议（按 ROI 排序）

1. **`uvicorn --workers 2`（必做）**：预估把 100 并发 P95 从 12s 砍到 6-7s，零代码改动。下次压测验证。
2. **同 query LRU 缓存 5min（高 ROI）**：重复问题（如"周工作 15 小时"被问 N 次）直接复用答案，跳 LLM 调用；按 query 字面 hash 即可。预估重复率 30-50%，高峰期可省 50% LLM 流量。
3. **embedding 并发化（中 ROI）**：当前 embed + chroma.query 是串行；用 asyncio.gather 并发跑两条 embedding 调用（如 hybrid RRF 算两个 query），省 ~200ms。
4. **监控告警（必做但低优先）**：跑个 cron 每分钟 curl /health + 数 query_log 增量，5xx 率 > 1% 时邮件/微信告警。
5. **不推荐**：拆 Chroma 为独立 server——成本高收益小，当前场景下不是瓶颈。
