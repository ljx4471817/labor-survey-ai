# LLM 瓶颈分析与上云影响（2026-06-29 思考稿）

## 一句话结论

**上云不能解决 LLM 慢的问题**——瓶颈在 DeepSeek 端（每账号并发连接数 ~45），不在你的服务器。我们的代码、机器、网络都是「旁观者」。真要突破，需要让**打到 DeepSeek 的请求变少**，而不是让发请求的机器变强。

---

## 1. 为什么 w1 / w2 都被卡在 11 QPS——数学解释

### 实测数据

| 并发 | QPS | P50 | P95 |
|------|-----|-----|-----|
| 1 | 0.33 | 2.8s | 4.3s |
| 20 | 5.9 | 3.3s | 4.6s |
| 50 | 10.7 | 4.5s | 6.4s |
| 100 | 11.4 | 9.0s | 11.9s |

### 推导

每个 chat 请求的生命周期：
1. 用户发请求 → 服务端接收（~10ms）
2. 走 Chroma + BM25 检索（~500ms）
3. **拼 prompt 后调 DeepSeek，等 LLM 流式生成完整答案（~3-4s）** ← 关键
4. 写 query_log + 返回（~50ms）

也就是说，**每个请求占用一个 DeepSeek 连接 3-4 秒**。

50 并发时：
- 理论 in-flight = 50
- 实际 in-flight = QPS × 平均耗时 = 10.7 × 4 ≈ **43**
- DeepSeek 把"用满 43 个连接"算作饱和，新请求开始排队
- 排队让 P95 从 4.6s → 6.4s

100 并发时：
- in-flight 还是 ~45（DeepSeek 上限）
- 多出的 55 个请求纯排队等连接
- P95 从 6.4s → 11.9s

**DeepSeek 默认账号的并发连接上限 ≈ 45**，不是 RPM 限制（2500 RPM = 41.7 RPS，我们实测 686 RPM，离 RPM 限制还远）。

## 2. 上云能改变什么、不能改变什么

### ❌ 不能改变的（LLM 端）

| 项 | 当前(本地) | 上云后 | 变化 |
|---|---|---|---|
| DeepSeek 并发连接上限 | 45 | 45 | **不变** |
| 单请求 LLM 生成耗时 | 3-4s | 3-4s | **不变** |
| 网络 RTT（你→DeepSeek）| ~50ms | ~30ms（同区域）| 可忽略 |

### ✅ 能改变的（你的服务端）

| 项 | 当前 | 上云后 |
|---|---|---|
| 服务可用性 | 单机 crash = 全停 | 多实例 + LB |
| 静态资源速度 | Cloudflare 边缘 | OSS + CDN（更快） |
| 部署/运维 | 手动 | 自动化 |
| 横向扩展 | 受单机限制 | 多 ECS 实例 |

**翻译给非技术**：把店开在更热闹的商业街不会让厨师变快，因为厨师不在你店里——厨师在 DeepSeek 那个中央厨房。你能做的是：让顾客点菜前先把常见 5 道菜做好放保温柜（缓存），或者让他们点完菜后边做边上桌（流式）。

## 3. 真正能突破瓶颈的方案（按 ROI 排序）

### 第一档：发布会前可做（投入小，体感或吞吐有改善）

#### A. LRU 缓存同 query 5 分钟 — **最高 ROI**（4-6h 开发）
- 同样 query（hash 一致）直接复用上次的 answer
- 预估缓存命中率 30-50%（"周工作 15 小时""自营+新开业"类反复问）
- 命中时 0 LLM 调用 → 直接腾出 DeepSeek 连接
- 实测预期：50 并发 P95 从 6.4s → 4s 左右，QPS 从 11 → 15-18

#### B. Top 10 高频问题静态答案 — **零 LLM 调用**（1-2h 开发）
- 把 `query_log.db` 高频 query + 已采纳 answer 抽出来，预存进代码/JSON
- 命中后直接 200，不进 RAG，不调 LLM
- 适合已经稳定、不需要 LLM 发挥的高频问题
- 缺点：KB 改了要同步更新（维护成本）

#### C. Streaming SSE（首字延迟优化） — **改善体感**（1-2h 开发）
- LLM 响应改为流式，前端逐字渲染
- **总延迟不变**（仍 3-4s），但**首字延迟 4s → 0.5s**
- 用户感知：从"卡 4 秒出结果"变成"立刻开始打字"
- 不解决 QPS 上限，但 300 调查员的 6s → 4s 体感差别巨大

### 第二档：突破 DeepSeek 并发上限（结构性改动）

#### D. 申请多 DeepSeek key + 轮询（2-3h）
- 个人/家庭账号 2-3 个，round-robin 分配请求
- 并发上限从 45 → 135
- **风险**：DeepSeek ToS 不允许多账号绕配额，账户可能被封（需先读条款）
- 备选：直接换 DashScope `qwen-max`（按 token 计费，无 RPM 限制，只受钱包限制）

#### E. DashScope qwen 替代 DeepSeek（半天）
- qwen-max-latest 与 DeepSeek-V3 质量相当
- DashScope 按 token 付费，没有 RPM/连接数硬限制
- 唯一的瓶颈变成钱（300 人 × 每日几十次 × token 单价 ≈ 月 ¥30-50）
- 代码改动：`config.py` 把 base_url 换一下

### 第三档：长期方案（用户规模到 1000+ 再考虑）

#### F. 阿里云 PAI 自托管 Qwen 7B（1-2 周）
- vLLM + A10 GPU 实例
- 单机 QPS 可达 50-100（取决于 prompt 长度）
- 投入：GPU 服务器 ¥3000-5000/月，或抢占式实例 ¥1500/月
- **当前 300 用户用不上**，QPS 11 已经够

## 5. 关键风险

1. **不要做"加 worker"**——已经证明无效
2. **不要买更高配置机器**——I/O bound，CPU/内存不卡
3. **多 key 绕配额有封号风险**——选 E 更稳
4. **流式响应要把前端 fetch 改成 EventSource/ReadableStream**——前端也要改
5. **静态 Top 10 要有失效机制**——KB 改了答案过时怎么办？
