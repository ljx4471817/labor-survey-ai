## 结论（出乎预期，必须如实报告）

**`uvicorn --workers 2` 没有带来预期的容量提升**。所有档位的 QPS 和 P95 变化都在 ±5% 噪声范围内。

### 关键发现：瓶颈不在 uvicorn，而在 DeepSeek API

观察：
- **w1（单进程）和 w2（双进程）在 100 并发下 QPS 几乎相同**（11.12 vs 11.43）——增加 1 个 worker 几乎没有增加吞吐量
- **w1 在 50 并发时 QPS 已经达到 11.17，100 并发仍 11.12** —— 拐点出现在 50 并发
- **w2 在 50 并发时 QPS 也是 10.7** ——同样的天花板

外推到机制：
- 单 worker 的 anyio 线程池（默认 40 token）已经能并行发出几十个 LLM 请求
- DeepSeek API 端的 RPM 限制（默认 2500 RPM ≈ 41.7 RPS）和并发连接上限才是真实瓶颈
- 加 worker 只是把同一批 LLM 请求从 1 个进程发 vs 2 个进程发，DeepSeek 端排队是共享的
- Chroma SQLite + BM25 的瓶颈也没有暴露出来，因为 LLM 已经先把整个系统拖在 11 QPS 上

## 决策建议

### 选项 A：接受 workers=2 部署但认清现实
- 启动命令保留 `--workers 2`（已写进 `start_tunnel.bat`）
- 收益：**单进程崩溃不影响服务**（worker 进程可被 master 重启）——是高可用收益，不是性能收益
- 性能 QPS 仍卡在 ~11（即 300 调查员 × 高峰期 50 并发档 ≈ 6.4s 响应，可接受）

### 选项 B：回滚到 workers=1
- 节省 ~250MB 内存（第二个 worker 进程）
- 性能相同，但失去单进程崩溃保护

### 选项 C：换真正的扩容方向
- **同 query LRU 缓存 5min**（高 ROI，零依赖）：预估省 30-50% LLM 流量，因为「周工作 15 小时」「自营+新开业」类问题被反复问
- **购买 DeepSeek 高 RPM 套餐**：直接突破天花板
- 这两个才是真正能让 QPS 翻倍的方向

### 我的建议
走 **A + 启动 LRU 缓存开发**。workers=2 已经改了，启动层面有了 HA 收益；LRU 缓存是真正的性能收益路径，约 4-6 小时开发量（含测试），可作为下一迭代任务。
