# 冲突预检 checklist（供 kb-update-workflow 引用）

> 这是 kb-optimize 的配套参考文档。新题入库时跑一遍，减少事后修复需求。

## 何时用

`kb-update-workflow` 的阶段 3（detect_gaps）之后、阶段 4（人工 review）之前。

## 检查清单

```
新 QA 即将入库，问以下问题：

□ 1. 新 QA 的 keywords 是否和现有 FAQ 高度重叠？（> 50% 相同）
    是 → 标记为"可能冲突"，进入第 2 题
    否 → 通过

□ 2. 新 QA 的 answer 结论和重叠 FAQ 相反吗？
    是 → 必须处理（三选一）：
         a) 给新 QA answer 加 scope 限定（"本条仅适用于…，不适用于…"）
         b) 给现有 FAQ answer 加 scope 限定
         c) 拆分成两条独立 QA，消除重叠
    否 → 通过

□ 3. 新 QA 和现有 QA 是"制度原文 vs 估算兜底"的组合吗？
    是 → 建议拆成两条（制度原文一条、兜底一条），避免「如果是…」误导分支
    否 → 通过

□ 4. 新 QA 的 question 用了「如果 / 一般 / 大概」等兜底措辞吗？
    是 → 在 answer 开头加适用/不适用声明
    否 → 通过
```

## 输出格式

```
[冲突预检报告]
新 QA id: <id>
冲突检查:
  □ 1. keywords 重叠: 是 / 否 → 重叠 id: <list>
  □ 2. 结论相反: 是 / 否
  □ 3. 制度原文 + 兜底组合: 是 / 否
  □ 4. 兜底措辞: 是 / 否
处理建议: <具体操作>
```

## 实操约定

- **预检不通过 ≠ 不能入库**，而是**必须处理冲突后再入库**
- **处理方式优先顺序**：加 scope 限定（最小改动）> 拆分条目（中等改动）> 合并条目（大改动）
- **每次预检结果留存**到 `reports/conflict-precheck-<date>.md`，方便回溯
